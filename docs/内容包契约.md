# 张翼内容包契约 v1

## 目的与边界

内容包让同一份用户材料在工作台得到更贴近品类的选择、推荐、首局草案和审查提示。内容包是**可反应的离线设计预设**，不能声称已读工程、跑过游戏或观察过玩家。当前只有战棋包完成这一闭环；棋牌和经营仍是有限的旧版首局候选，不能标成完整内容包。

四条独立轴：**品类**决定主要玩法取舍；**创作路线**决定做模组、新游戏、独立短局、比较方向或修现有项目；**工程条件**记录已有代码、工具及其证据状态；**风格**决定表达与感受。选了战棋不等于有战棋工程；带工程不等于某一种品类；古风也不能推断玩法规则。一个项目可以有混合品类，但 v1 不自动拼接多个品类包，应让用户选首局主导玩法，再在审方案里处理第二玩法。

## 统一格式

工作台的可执行数据位于 `nest/content-packs.mjs`。统一封套是 `schemaVersion / id / axis / value / title / status / boundary`，其中 `axis` 可为 `genre`、`style`、`engine`；只有 `complete` 的包可自动进入推荐。三类包另有各自的内容区，不能互换职责：

| 字段 | 用途 |
| --- | --- |
| 品类 `genre` | `firstChallenge` 给首局目标与 2–4 个行动、胜负候选；`questions` 给少量品类选择题；`prototype` 给各目标的关卡草案、最小循环、验收和暂缓项。 |
| 风格 `style` | `presentation.visual / text / feedback` 分别说明画面可读性、文本表达和操作反馈；`verification` 给呈现核验动作（怎样证明风格确实传达到位）。它不能定义首局胜负。 |
| 引擎 `engine` | `capabilities` 只记可用能力和版本范围；`verification` 给在目标工程里要执行的核验动作。它不能替用户决定品类。当前只有格式槽位，还没有完整引擎包。 |

品类题每题有稳定 `id`、`topic`、通俗问题、为何要选、选项影响、默认值、深度、适用条件和上游依赖。

选项只存 `value / label / effect`。推荐理由由调用规则生成，并显式标来源：用户原话的待确认线索、已确认记录加内容包、或纯内容包预设。新增包必须通过格式校验、覆盖无工程与有工程两条路径，并证明它确实改变至少一道设计判断；不能只换题材词。

## 调用次序

1. 先读用户已确认的项目决定；旧决定比预设优先。只从**游戏想法**暂推品类，不从工程条件推断；用户原话可触发**待确认推荐**，不能升格为确认决定。若原话与明确品类选择冲突，尊重明确选择并显示可修改入口。
2. 再确定创作路线和首局主导品类。工作台仅按主导品类装载一个包；没有完整包就退回通用题库及有限候选，标明覆盖不足。
3. 包改动首局候选、可选的深入问题、立项草案和审方案提示。必要路径保持短：独立短局问首局目标与首次试玩观察；沿用工程做新游戏问首局目标与复用意图。品类包的细化题可展开或暂拟，不强制填满。
4. 工程条件只决定是否问复用、怎样核验运行，以及制作边界；**不得改变品类推荐的依据**。以后引擎适配器只能提供接口、能力、限制和验证动作，不能凭代码现成替用户决定玩法。
5. 用户改首局目标时，下游战术选择标为需复核；改品类时，旧品类决定保留历史并标为需复核。包升级要保持问题 ID 和选项值稳定，或提供迁移规则。
6. 导出区分用户已定、预设暂拟、需复核与未定。包的最小循环是制作草案；实际运行和真人试玩另取证据。

## 战棋包 v1 的设计职责

第一局可选守点、护送、击败关键敌人；进一步只围绕回合核心取舍、地形用途、敌方回应三件事展开。推荐会随用户原话和已选首局目标变化；用户始终能选其他选项。立项草案写出最小可玩循环、胜负验收和首版暂缓项；审方案提醒检查可读的威胁、有效的走位、明确的失败原因。首版暂缓职业树、大量兵种、战役地图和只增加复杂度的地形。

这个包只解决**战棋短局先怎样定方向**，不包含战棋工程代码、不声称覆盖全部战棋流派，也不替代对现有工程的只读盘点。

## 后续顺序

1. 用陌生于该包的起点复测战棋：有工程、无工程、只给题材、混合品类、旧记录切换品类；记录用户理解和离开位置。AI 合成走查与真人反馈分别记，不混为一谈。
2. 调研独立游戏中常见的品类与实际需求，再决定下一个完整包。候选优先看**模拟经营、增量挂机**；棋牌博弈可以利用现有首局候选升级。调研前不预定优先顺序或填充未经验证的引擎样板。
3. 另建风格包契约与第一批风格包，候选覆盖**古风、西幻、日式幻想、赛博朋克**，再逐步扩充。风格包应改变呈现、文本与反馈，不替品类包定胜负和回合规则。**风格包另需 `verification`（呈现核验动作）**：只有 `presentation` 三槽描述"风格长什么样"，`verification` 才回答"怎样证明风格传达到位"（联想是否稳定指向、维度评分是否达标）；这条在古风包施工时新增，与引擎包既有 `capabilities ＋ verification` 同构。
4. 最后按真实项目需求建设引擎适配器，并用目标版本运行证据验收；不在 skill 里堆大量未经维护的代码。
