# 工作台状态与导出契约（施工草案 · 2026-09-26）

## 为什么先定这份契约

HTML 是第一种界面，终端可能是下一种。两者必须读写同一份项目状态，
生成同样的交接文档。否则每增加一个入口、换一套界面，就得重新解释整个项目。

## 项目状态的最小单位

先保留六类记录，所有记录有稳定 ID、创建时间、最后修改时间和来源：

| 记录 | 它回答什么 | 必须区分的状态 |
|---|---|---|
| 输入 | 用户最初说了什么、带来哪些文件或参考游戏 | 用户原话 / 张翼归纳 |
| 目标 | 用户现在想得到什么：模组、短局、完整游戏、修改现有项目等 | 已确认 / 暂拟 |
| 选择 | 当前分叉、选项、推荐、用户选择及理由 | 张翼建议 / 用户拍板 / 已撤回 |
| 判断 | 张翼保留、暂缓、否决了什么及代价 | 过 / 缓 / 否 / 待证据 |
| 证据 | 纸面推演、程序运行、真人反馈分别说明什么 | 来源、样本与口径、适用边界 |
| 产物 | 小样、裁决书、交接文档等在哪里、对应哪个状态版本 | 草稿 / 已生成 / 已运行或已核验 |

入口类别只是输入标签，可以同时有多个，也可以后补；不写成互斥的工作流枚举。
创作路线是可更改的目标。每项选择标记它依赖什么、会影响哪些后续选择和产物。
修改旧选择时，保留旧记录并让依赖项变成“需复核”；不能悄悄把旧文档留作现状。

## 导出规则

所有文档从某个**明确的状态版本**生成，页首标版本、生成时间与来源文件。
导出包至少含：

1. 可读的项目总览：玩家做什么、当前路线、已拍板/暂拟/待验证。
2. 给下一位 AI 的交接：项目身份、目标平台、文件地图、不得擅改的决定、
   可自行暂拟的细节、未决问题、下一步要交什么及验收条件。
3. 结构化项目状态：让界面和工具继续编辑，不靠从散落的 Markdown 反向猜测。
4. 已存在的阶段裁决书与小样说明；没有的标“尚未形成”，不生成空壳假文档。

文档覆盖开发所需的主要方面，但未讨论或未验证的内容写“未定”和下一次决定条件，
不能为了“详实”编造数值、技术选型或玩家反馈。不同模型收到的文件应保持一致；
接手模型产出后，再根据决定 ID 和验收条件检查是否跑偏。

## 共享核心与界面

第一版把状态读写、选择变更、依赖失效、导出生成做成不依赖页面元素的模块。
HTML 负责展示与操作；将来终端调用同一模块。模型连接与本地文件读写另作适配，
不写死在状态逻辑里。现有离线 HTML 可先通过导入/下载文件完成闭环。

## 第一条可失败的验收

用“喜欢一款策略游戏，想做某历史题材版本”开局，完成路线与一个胜负目标的选择，
导出项目状态和交接文档；修改路线后重新导出。应满足：

- 旧选择仍可追溯；依赖旧路线的目标显示“需复核”。
- 两次导出的文档与结构化状态一致，明确说明哪些是用户拍板、哪些只是建议。
- 另一模型只看导出包，能正确复述当前短局、已定边界、下一步验收条件。
- 界面没有把未做出的模组或未经运行的小样标成“可玩”。

上述流程在真实宿主与陌生用户中执行前，只是设计契约，不能算验收通过。
