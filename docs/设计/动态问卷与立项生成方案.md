# 动态问卷与立项生成方案（草案 · 2026-09-26）

## 这次实操暴露的问题

一个真实项目已经给出引擎、玩法系统、参考风格和设计顺序。张翼仍在聊天里连续十余次给三选一，虽能逐项准确拍板，却让用户明确感到疲劳。本观察来自本会话一位用户的一次实操；它足以触发产品修正，不足以证明所有用户的最佳问卷长度。

问题不在选择题本身，而在**每答一题都要等一次模型往返**，且用户看不到剩余问题、依赖顺序和何时能得到立项书。发现问题时，工作台只有路线和第一层重点的预设选择；本页末尾记录后续施工状态。

## 推荐的使用流程

```text
自由输入想法/导入现有材料
    ↓
张翼先给一页可反应的概念草案，并识别已知条件
    ↓
页面内生成本项目的动态问卷
    ↓
用户按主题连续作答；条件分支即时增删；可暂停、回改、跳过可暂拟题
    ↓
显示答案检查页：已拍板 / 张翼暂拟 / 冲突 / 待验证
    ↓
生成可修改的立项书草案 + 结构化项目记录 + 开发交接
    ↓
需要更深设计时，再进入系统/叙事/制作问卷与可玩小样
```

首轮仍先给草案：只抛出一份空问卷会让玩家觉得自己必须先成为策划。问卷用于快速收集偏好和边界；张翼负责把答案变成有取舍、有缺口的方案。生成立项书后，用户可随时回到某题，相关段落标记需重算。

## 题量：首版约 40 题库，实际展示量待测

首版目标是约 40 张**题目卡**，覆盖体验、参考路径、玩家身份、首局行动、循环、胜负、角色、制作范围和验证。对某个项目，只有满足条件的题才出现：

| 题组 | 题库张数（首版目标） | 只在什么情况下展开 |
|---|---:|---|
| 起点与参考路径 | 5 | 缺少想法，或用户明确想复刻、做模组 |
| 玩家承诺与入场 | 6 | 体验目标、身份或头十分钟尚不清楚 |
| 核心循环与局间行动 | 7 | 多局、多阶段或需要探索/经营时 |
| 胜负、失败与成长 | 5 | 游戏存在失败、损失或长期积累时 |
| 人物与世界回应 | 5 | 角色和世界会影响玩法时 |
| 首版系统与制作范围 | 8 | 用户已有系统、引擎或大量功能设想时 |
| 可玩切片与验证 | 4 | 要求制作、试玩或交给下一模型时 |
| **合计** | **40** | **条件出现，不逐人全问** |

- 用户已明确的信息直接预填，旁边标“来自你的原话”，允许纠正，不重问。
- 结构性选择只问一次；后续题根据答案改变。例如选择“基于现成工程做新游戏”，跳过引擎选择；选择“没有战斗”，不问战斗系统。
- 高把握、低成本的小决定由张翼给暂拟值，在答案检查页集中展示，玩家可展开修改。
- 先完成一条能生成立项书草案的必要路径。此前估计的 12–18 道亲答题仅是待测假设，不是验收门槛；约 40 道是题库规模，也不是每个人的必答量。实际展示和作答数量由不同起点的真实试用决定，不能把答题数当完成度。
- 对资料充分的现有项目，本次 v18 已拍板的项目身份、舞台、循环及部分系统应直接进入答案页；问卷只问尚缺且影响产出的事项，不重新跑四十题。

用户提议的“30–50 题”适合作为题库和深入模式的规模。如果把 30–50 道都设为第一次生成立项书的必答门槛，很可能重复制造这次的疲劳；这一点应通过真实试用验收，而不是仅凭策划直觉宣称。

## 已有项目从当前进度接续

`0926casino` 是首个迁移样本，不从头立项。其 `zhangyi-workbench/zhangyi.project.json` v18 已保存 13 项用户选定的方向与系统决定。工作台导入后，应先展示一页现状摘要：已确认、张翼暂拟、未定、互相冲突。已确认决定映射到稳定题目 ID 并预填，跳过对应题；不能映射的原决定也须保留原文和来源，列入“待归类”，不能丢弃或默默重问。只对影响下一份产出的缺口出题。

这个项目已经进入逐系统取舍，接续时不强迫重看零点子入口，也不假装此前决定尚未发生。工作台可先由已知内容生成一份标明缺口的立项书草案，再通过问卷补齐；后续未定的技能、物品/商店、地图探索和问答系统在适当阶段继续审。若导入内容与题库预设相冲突，集中提示用户核对，不由系统覆盖用户已确认的决定。

Codex 仍承担张翼的判断与文档生成，HTML 工作台承担可见的问卷、状态和回改入口。两处使用同一份项目状态；当前页面仅能导入、展示和导出记录，尚不能完成上述接续问卷和立项书生成。

分支例子：用户选“只做一局短小样”，隐藏多章节推进、长期养成与完整地图规模题；用户选“已有可运行 Ren'Py 骨架”，引擎版本和工程路径从输入预填，只展示“现成系统哪些有助于玩家体验”；用户选“战棋”，再展开回合目标、单位互相影响和失败条件，其他类型不见这些题。

## 每张题目卡的数据契约

```json
{
  "id": "loop.between_rounds",
  "stage": "core_loop",
  "prompt": "两场赌局之间，玩家最想做哪件事？",
  "why": "这个答案决定局间玩法的重心和要做的内容量。",
  "showWhen": { "all": ["project.has_multiple_rounds"] },
  "answeredBy": ["user_quote", "existing_decision"],
  "options": [
    { "id": "prepare", "label": "为下一局找线索、谈条件", "tradeoff": "布局感强；需要让准备在下一局兑现" },
    { "id": "explore", "label": "调查这个地方的秘密", "tradeoff": "悬念强；可能与下一局脱节" }
  ],
  "recommended": "prepare",
  "recommendationReason": "当前项目把斗智准备作为体验核心。",
  "importance": "directional",
  "allowProvisional": false,
  "writesTo": ["decisions.loop.between_rounds"],
  "invalidates": ["decisions.systems.map", "artifacts.kickoff_brief"]
}
```

题目 ID、条件和依赖由版本化题库管理；选项文字与推荐理由可以由张翼结合项目材料生成。模型生成的题必须经过校验：有稳定 ID、2–4 个真正不同的选项、各自后果、推荐理由、默认值、依赖以及它改写哪一条项目状态。校验失败时留在草案，不伪装成可作答的正式题。

页面保存每题的 `answer/source/status/version`，其中来源区分用户选择、用户原话预填、张翼暂拟、现有工程证据。用户改上游答案时，受影响的下游题和立项书段落变成“需复核”，不悄悄沿用旧回答。

## 页面交互

问卷在 HTML 工作台**直接作答**，不是下载一份静态文件再上传。页面按“想做什么体验 → 玩家怎么玩 → 输赢与人物 → 制作范围”分组，一屏显示当前组与上一组结论；答完选择题就即时更新下一题。可返回、暂存、继续，显示“还缺哪些关键决定才能生成草案”，不显示制造压力的“40 题做了 7 题”进度。

“跳过，先按张翼建议”只适用于低风险或可逆的题，答案状态是**暂拟**。改变项目身份、核心玩家行为、胜负代价及高成本制作范围的题，用户需要主动确认或在草案中明确保留未定。页面可导出**已作答的项目状态、立项书和交接**；动态问卷本体留在工作台运行，不作为需下载后填写的表格。

问卷所需的实时项目化选项、推荐和新增分支，必须接通张翼运行宿主与页面之间的模型/本地文件桥。纯离线 HTML 可以运行经审查的固定题库与确定性条件分支，但必须标明它是预设，不称为张翼当场的专业判断。首版实现可先用固定题库跑通一条路径，再接模型适配层。

## 立项书如何生成

答案检查页通过后，从同一份 `zhangyi.project.json` 生成《立项书草案》，至少包括：一句玩家承诺、玩家身份与首十分钟、核心循环与胜负、参考对象的借用边界、关键角色、首版范围、最大三项风险、第一份可玩切片、未决定项及验证计划。每个关键段落能追溯到用户回答、张翼暂拟或工程证据。没有足够依据的数值、商业结论和“已经好玩”不得补写。

问卷完成不等于立项通过。张翼仍须做冲突检查（例如“输了即死”与“输了还能继续剧情”）、范围检查和证据标注；发现重大冲突时在答案检查页集中让用户处理，避免回到一轮一问的拉锯。立项书先作为可修改草案交付；逐系统规格和制作交接可以继续深化，不把 40 题伪装成完整游戏设计文档。

## 施工与验收

1. 题目契约与依赖引擎：题库、条件显示、预填、答题状态、上游修改失效、断点续填；状态核心不依赖 HTML。
2. 页面问卷与答案检查：一条“零点子”和一条“已有工程”路径，支持页面内即时分支、返回、暂拟和继续。
3. 立项书生成：同源生成草案、总览和交接；对照题目 ID 检查每条关键主张与已定/暂拟边界。
4. 接入张翼：让模型只处理项目化题目与判断；输出经 schema 校验后才进入页面，失败时保留已答内容。
5. 真实试用：至少覆盖零点子、单一玩法、参考游戏、已有工程四类入口。记录用户实际回答数、用时、退出点、术语困惑、能否复述方案；由未参与开发的用户验证，样本量和口径逐次报告。

首条可失败的验收：把 `0926casino` 的 v18 项目记录导入新页面后，13 项已定决定均被保留，已定方向与系统取舍不再重问；用户能在页面内回答剩余关键分叉、回改一项并看见受影响题重算，随后得到标明“已确认/暂拟/未定”的立项书草案。记录实际展示题数与作答题数，不预设合格题量。

**施工状态（2026-09-26）**：固定 40 题题库、条件显示、页面内答题与回改、已有决定预填、低风险可选题的“预设暂拟”、同源立项书草案已接线。v18 的 13 项决定全部映射，必要路径目前显示 12 道缺口；这只是一个项目的结果，不代表最佳题量。核心逻辑测试与页面导入/试答已通过。仍待：张翼模型桥接、项目化选项和推荐、冲突审查、更有推导性的立项书，以及未参与开发的用户实测。当前草案是结构化汇总，不得称为张翼完成正式立项评审。

**v32 实操修正**：同一位用户完成了这条必要路径，得到 25 项已确认决定和 v32 项目包。反馈认为集中答题可用，但部分选项含糊、推荐不够可见；另发现“输局带着损失继续”与后来选的“学到规则后重试”需要核对。工作台已加长关键选项的后果说明、显示有依据的离线推荐、对这一组明确冲突给出提示并写入草案。推荐不会自动改掉用户答案。页面顶部可选项目目录，本地服务直接写入版本化 ZIP，不覆盖同名旧包；浏览器下载仍可用。内置浏览器没有原生目录写入接口，因此依赖本地服务。通用冲突审查、模型项目化判断、立项书推导和陌生用户实测仍待施工。
