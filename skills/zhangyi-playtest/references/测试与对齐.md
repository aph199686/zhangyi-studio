# 测试与对齐（走查标尺 + 问题清单 + 尖叫度 + 五节点沟通）

> 素材来源：能力单元 04（体验走查与问题清单）、05（尖叫度测试）、
> 03（研究项目沟通对齐）。标注"张翼推断"的条目是独游降级建议。

## 体验走查：先立四层标尺

| 层级 | 判定 |
|---|---|
| 有用 | 提供玩家想要的内容与功能，打中痛点——可能达成目的但损害其他系统 |
| 可用 | 可学习、效率高、容错好——能达成目的且不损害其他系统 |
| 易用 | 最小化负担，玩家想要啥正好给啥——轻易达成目的甚至兼顾其他系统 |
| 惊喜 | 优于市场水平且超出预期，是别人没有的内容 |

- [ ] 惊喜三属性：相对的、动态的、向下兼容的——情理之中，意料之外。
- [ ] 品质判断靠对比：与玩家预期比、与竞品比。
- [ ] 警惕晕轮效应：短板会被放大拖累整体口碑；独特性本身也是品质维度，
  不必只向上卷。

## 可用性走查四性

- [ ] **可学习性**：需要时才给引导；不同时出现多个指引；指引不用大段文字；
  学习有效且持续。
- [ ] **容错性**：产品少制造错误；用户低错误率；给改正机会
  （消耗稀有物品时有没有保护锁）。
- [ ] **高效性**：功能充分、架构清晰、信息分层，让每一屏都有作用。
- [ ] **安全性**：关键操作有防呆与确认。

## 交互走查要点（交互是玩家和游戏的中介）

- [ ] 高频操作是否顺手、是否分布在设备操作热区。
- [ ] 控件是否符合认知习惯；位置、关系、尺寸是否突出重点。
- [ ] 新手引导自查：知识点信息量是否严重多于竞品？前期投放是否过多、
  哪些可后延？投放节奏与密度是否合理？是否滥用强制引导？
  是否一次引导多个知识点？引导文字是否过多或形式不易理解？
  ——目标只是"学会知识点"，多 ≠ 好。

## 走查方法三选或组合

跑查评估（自己按标尺过一遍）/ 竞品分析（同维度对比）/
测试评估（带真人玩家跑）。开工前写明：本次用哪种、覆盖哪些模块。

## 问题清单（每份测试报告必附）

三档写法，按问题复杂度选：

1. **形式一**：问题内容 + 影响/后果展开。
2. **形式二**：问题内容 + 影响/后果 + 截图说明。
3. **形式三**：问题内容 + 后果 + 原因的详细解释（用于玩法层面的深层问题）。

六类写法错误自查：

1. [ ] 一条说了多个问题。
2. [ ] 描述模糊。
3. [ ] 没区分玩家的 need 和 want——want 不是游戏问题。
4. [ ] 没写后果。
5. [ ] 玩法层面问题没分析原因。
6. [ ] 把体验问题混同于 bug——一级体验问题 ≠ bug。

清单登记后进入跟进流程（见下方节点 5），不许写完就沉底。

## 尖叫度测试（Demo 期核心体验验证）

回答一个问题：**核心玩家玩到核心循环的第一小时，会不会尖叫。**
低分是最便宜的预警。

### 测什么、不测什么

- [ ] 只衡量**短期核心体验的吸引力**。
- [ ] 测不了：耐玩性、用户增长、商业表现——那些归留存分析、导量验证、
  商业化评估管，别越界。
- [ ] 解读口径：分数高低不直接决定成败，但低分强烈提示对核心玩家
  吸引力不足、第一小时流失风险高。

### 形态与采样规程

- [ ] 两种形态：街坊式（外部真实场景拦访）/ 实验室式（受控环境）。
  两种场景分数口径有差异，不与别家场景混比。
- [ ] 被测物：包含游戏核心内容的垂直切片。
- [ ] 单次体验时长约 15–30 分钟。
- [ ] 样本量 30–40，覆盖 2–4 类目标玩家，必须涵盖核心、次核心、
  泛玩家三层。
- [ ] 评分细则（怎么算分、分数线怎么解读）原材料未展开——**盲区在案，
  不许现编分数线**。

### 质量四原则（自查闸门）

- [ ] **有效**：多地取样、大样本。
- [ ] **真实**：外部真实玩家，接近真实游玩环境；不给奖励或采用随机拦访，
  避免"拿钱说好话"。
- [ ] **客观**：评估独立运转，多名执行者交叉，研究员不替玩家下结论。
- [ ] **标准**：标准化取样、标准化清洗（清洗细则原材料未展开，待补）。

### 产出与跟进

- [ ] 报告按玩家分层（核心/次核心/泛）分别呈现，不是只给一个总分。
- [ ] 与历史测试、竞品的同类数据对照——对照数据靠平时积累，现找找不到。
- [ ] 低分触发：回核心体验设计找原因，而不是急着加内容。

## 研究项目五节点沟通对齐

把研究当"信息服务产品"来生产：五个节点各有必须达成的对齐目的，
缺一个，返工在路上。独游的"委托方"可以是合作者、发行方，
或三个月后的自己——节点一个都不能省。

- [ ] **节点 1 · 需求沟通**：搞清真正要解决的问题。问清六个问题——
  希望解决什么问题？为什么会产生？当初的设计思路？结果怎么使用？
  产出什么才可用？后续迭代计划与时间？
- [ ] **节点 2 · 方案沟通**：对齐时间、地点、方式、人数与覆盖问题；
  写明需要对方配合的准备事项；邀请委托方旁观测试
  （结论被直观吸收的最便宜方式）。
- [ ] **节点 3 · 结果沟通**（报告撰写前）：第一时间给初步结论用于迭代。
  话术结构："从测试结果看，我们估计答案是……/玩家表现是……/
  还有意外发现比如……" 现场确认：问题是否已解答？要不要补测加测？
- [ ] **节点 4 · 报告确认**（发出前）：确认对方全部理解、无疑问再正式发出；
  核对抄送范围；请对方回复报告的应用规划，防报告沉睡。
- [ ] **节点 5 · 问题清单跟进**：清单登记后定期核对迭代进展；
  跟进中发现的新问题触发下一轮研究。

贯穿纪律：

- [ ] 沟通姿态：主动、灵活、反复、有意义，不干扰对方正常工作。
- [ ] 传递口径三原则：反馈的准确性、传递的价值量、结果的一致性；
  拿不准"不妨多问几次"。
- [ ] 不跨职能：研究给依据，不替产品做决定。

## 独游降级注记（张翼推断，非原材料）

- 尖叫度样本量 30–40 对独游偏高，可等比缩小，缩了就在报告标注
  置信度下降；分层（核心/次核心/泛）不许缩没——三层变一层等于没测。
- 街坊式场景：展会、社区聚会、校园、线上随机邀约都成立；
  自己的粉丝群不算"外部真实玩家"。
- 没有实验室就用受控的线上连线 + 录屏回看；"多名执行者交叉"
  降级为同一份录像隔日复看，并在口径里写明是单人执行。
