# 框架理解与目录整理

对应接管流程第 3、4 步。目标：**快速、深度**建立对既有项目框架与目录的理解；
整理永远走"报告 → 授权 → 动手"，不得自动化跳过授权。

## 项目地图（第 3 步产物一）

按七层写，**每条都要能指到具体文件路径**；指不到的标"未定位"，不许编路径。

| 层 | 要回答的问题 | 示例证据 |
|---|---|---|
| 入口 | 玩家/程序从哪里开始 | 主场景、main 文件、index 页 |
| 构建与运行 | 怎么构建、怎么跑起来 | 构建脚本、引擎工程文件、命令 |
| 核心模块与职责 | 每个模块管什么、边界在哪 | 目录与关键文件，逐一标注职责 |
| 数据流向 | 状态从哪产生、流经哪、落到哪 | 存档读写、事件总线、网络同步点 |
| 外部依赖 | 依赖什么引擎/库/服务、版本 | 依赖清单文件、插件目录 |
| 测试与门禁 | 有什么自动化验证、怎么算过 | 测试目录、CI 配置、校验脚本 |
| 已知禁区 | 哪些地方用户明令不许碰 | 用户口述、项目文档红线 |

写法纪律：

- 先读构建/配置文件与入口，再顺依赖向外扩；不逐文件通读，按"改这条任务要碰哪"
  决定读多深。
- 模块职责用一句话写；写不出一句话职责的模块，标"职责待清"，进目录体检报告。
- 地图是给下一个会话（可能是另一个 AI）读的：写路径，不写"那个处理战斗的文件"。

## 目录体检报告（第 3 步产物二）

逐目录判定四类之一：

- **职责清晰**：名字与内容一致，不动。
- **混装**：一个目录装了多种职责，列出混了哪几类。
- **死重**：构建产物、废弃副本、无人引用的旧版；给出判定依据（无引用证据），
  不凭名字猜。
- **历史包袱**：能跑但结构挡路（命名误导、层级过深、循环依赖），写清它挡了什么。

报告只含**报告与建议**；任何"建议删除"都进第 4 步的删除类清单，不在本报告里动手。

## 整理授权流程（第 4 步）

1. **默认不整理**。第 3 步的产物永远是报告，不是动作。
2. **四类清单**：移动 / 重命名 / 合并 / 建议删除，逐条写
   **理由 + 影响面 + 可逆性**。影响面要落到具体文件（哪些引用要改）；
   可逆性分"可一键还原 / 需手动还原 / 不可逆"。
3. **删除类单列**：单独一节、单独明确风险、**单独授权**。不可逆的删除建议，
   默认改为"移入 `_archive/`"。
4. **授权要显式且针对清单**：用户逐条或整批批准均可，但"你看着办"不算授权。
   未批部分留在报告，不缩小范围硬做、也不扩大范围顺做。
5. **动手纪律**：可逆优先（移动 > 删除，复制 > 覆盖）；动手前**先备份**，
   备份位置写进整理说明；每动一类验证一次项目仍能构建/运行（有门禁跑门禁）。
6. **整理说明**：完成后写清——做了什么、备份在哪、如何还原、遗留问题；
   末尾张翼署名。

## 打标签边界（用户已拍板：两者都要）

- **项目根标记文件**：在用户项目根的 `zhangyi.config.md` 补一段接管标记
  （无此文件则新建），内容含：接管日期、接管前状态摘要一行、台账位置
  （`ledger/接续台账.md`）。只此一处项目级标记。
- **整理说明署名**：整理说明文末署名"张翼 Spread the Pinions · 接管整理"。
- **禁止**：在每个目录里撒标记文件；在用户源码的注释头里打标；
  改用户源码文件只为署名。标签是档案，不是涂鸦。
