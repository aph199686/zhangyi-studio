# 任务编排与完成标准

对应接管流程第 5 步。这是 takeover 最值钱的一层：把"还剩一堆事"变成
"谁在挡谁、这批做哪两三条、怎么算做完、这批不做什么"。

## 工作分解

- 把剩余工作拆成**可交付条目**：每条有明确产物（一个功能、一份报告、一次迁移），
  不写"继续完善战斗系统"这种没有边界的条目。
- 条目粒度：一条 ≈ 一个会话能做完或能干净中断的工作量。拆不动的写"待拆解"，
  状态标**待办**，不硬猜子任务。
- 每条落台账，编号 T-001 起（见 [接续台账模板.md](接续台账模板.md)）。

## 依赖与优先级

- 标明**谁挡谁**：T-003 依赖 T-001 写进台账"依赖"列；被挡的不许插进当前批。
- 先做顺序的判据（按序）：挡别人的先做 → 风险最大的先做（早死早超生）→
  用户急的先做。判据冲突时给用户选择题，不替他排。
- 里程碑单列：标**日期 + 验收方式**（能跑通什么、谁来看、看什么），
  不写"大概什么时候"。

## 批次

- **每批 2~3 条**，沿用 relay 小步走纪律——任务量超过单轮承受力是上下文爆炸
  与会话崩盘的头号诱因，这条踩过血，不许突破。
- 每批派活时写清：本批条目、各自 DoD、**显式裁剪**（这批**不做什么**——
  列出最容易被顺手带上的相邻工作，明确不做）。
- 批内完成一条汇报一条，不憋到最后批量汇报。

## 完成标准（DoD）

**先由张翼推导**，用户可改。格式必须是：

> 怎么算这条做完：<可观察的证据形式>

可观察的证据形式只有四类：**截图 / 数字 / 可运行结果 / 代码位置**。
例：

- 坏例："存档功能做好了"。
- 好例："怎么算这条做完：游戏内存档后重进，金币数与存档前一致；给一次实际运行的
  输入输出记录；代码位于 `save/system.gd`。"

纪律：

- 推导不出 DoD 的条目，状态标**待复核**，不许带着空 DoD 开工。
- DoD 不达标的条目不许标"已定"；部分完成就写部分完成的证据。
- 验收时按 DoD 逐条对证据，不接受"应该没问题"。

## 每批收尾

直接走 `zhangyi-relay` 场景 C：落交接段（遗留待办编号 / 新沉淀红线 / 新环境坑），
并同步更新台账五态。不在本 skill 重复实现交接段格式。
本批产生的可复用知识按 [项目维基.md](项目维基.md) 蒸馏 0~3 条进 `wiki/`；
没有可沉淀的就是 0 条，不凑数。

## 反模式

- 一批派 10 条：上下文爆炸后，完成状态全靠回忆补。
- DoD 写"做完了""没问题了"：无法核验的完成标准等于没有标准。
- 不裁剪：每批都顺手带上三条相邻工作，范围永远收不住。
- 里程碑写"下个月差不多"：没有日期与验收方式的里程碑是愿望，不是计划。
