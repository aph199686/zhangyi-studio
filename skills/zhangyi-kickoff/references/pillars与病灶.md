# Pillars 与病灶（判别法）

## 病灶判别：问题 vs 愿望

| 写法 | 是病灶吗 | 为什么 |
|---|---|---|
| "我想做一个很酷的游戏" | 否 | 愿望。没有指出谁痛苦 |
| "同类游戏玩到第三局就没有新东西了" | 是 | 具体、可观察、指向设计动作 |
| "玩家不懂我的数值深度" | 存疑 | 可能是病灶（信息设计失败），也可能是借口（数值其实没深度）。需要证据 |
| "市面上没有 XX 题材的游戏" | 否 | 市场空白不等于玩家需求。空白的原因可能就是没人要 |

病灶三问：① 谁在不爽？② 什么时候不爽？③ 你怎么知道（证据还是猜测）？
三问都答得上，才是真病灶。猜测可以立项，但必须标注为猜测。

## Design Pillars 判别

支柱是**不可妥协的承诺**，不是优点清单。

| 写法 | 是支柱吗 | 为什么 |
|---|---|---|
| "画面精美" | 否 | 无法执行：什么算精美？谁来判？ |
| "一局不超过 5 分钟" | 是 | 可检验：任何方案让它超 5 分钟，方案死 |
| "信息即资源" | 是 | 可执行：任何与信息无关的新资源提案直接否 |
| "创新" | 否 | 口号。所有游戏都想创新，它不过滤任何方案 |

支柱的检验：**它能否杀死方案？** 一条杀不死任何方案的支柱是装饰。
3~5 条为宜；超过 5 条，说明还没有真正取舍。

## 病灶与支柱的关系

病灶是"要治的病"，支柱是"治病的规矩"。
立项裁决书里两者必须同时出现：只有病灶没有支柱，方案没有过滤器；
只有支柱没有病灶，规矩不知道在保护什么。
