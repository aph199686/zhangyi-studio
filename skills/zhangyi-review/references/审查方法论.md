# 审查方法论（口径 / 分级 / 证据）

## 证据口径（审查开始前声明）

审查报告的可信度 = 它声明的方法 × 它遵守的程度。开始前写清：

- **审查对象**：哪些目录、包、版本、时间段（快照时刻）。
- **方法**：只读 / 跑构建 / 跑测试 / 实机 / 外部资料查询——
  做了什么写什么，**没做的明确列入"未覆盖"**。
- **路径简称**：长路径建简称表，保证后文每条证据引用可操作。
- **副作用声明**：审查过程是否对项目产生了任何写入
  （包括报告文件本身）。

**只读审查就声明只读。** 没跑过构建说"构建应该没问题"，
这一个"应该"就能毁掉整份报告的可信度。

## 核查纪律

1. **以现有实现为准**：历史文档里的"已修复""全绿"是线索不是证据。
   证据 = 当前文件内容、元数据、哈希、Git 状态、可复跑的命令输出。
2. **证据到行号**：每条结论给 `文件:行号` 或命令 + 输出摘要。
   给不出证据的结论，降级为"待补证"——降级不丢人，瞎给证据才丢人。
3. **抽样要报口径**：哈希比对、抽查类核查，写明抽了多少、怎么抽的；
   抽样证明不了全量，报告里就这么写。
4. **外部资料留来源**：平台政策、法律条文、市场价格，
   给官方链接 + 查询日期（政策会变，价格会变）。

## 六级结论分级（每条结论必须挂级）

| 级别 | 含义 | 典型形态 |
|---|---|---|
| 已核实事实 | 当前文件/元数据/哈希/官方资料可确认 | "164 个对应文件 SHA-256 一致" |
| 静态路径问题 | 代码/数据有明确问题，未实机复现 | "星级计算把持有过当打出过（`x.js:256`）" |
| 条件性风险 | 特定条件下可能触发，需专项验证 | "该 API 在 Win10 旧版可能缺行为" |
| 制作建议 | 决策建议，非强制规则 | "建议 Windows x64 单平台先行" |
| 工作量估算 | 用于立项比较，非报价非承诺 | "约 2–4 周，误差 ±50%" |
| 待补证 | 证据链不足 | **不等于有问题，也不等于没问题** |

风险三级：
- **高**：商业上架硬门槛、进度丢失、结算错误、质量门禁失效、
  显著改变路线成本
- **中**：影响体验或维护，有变通路径
- **低**：瑕疵与改进项

## 报告骨架（审查报告的通用结构）

1. **阅读导航**（长报告必备）
2. 范围、方法与证据口径
3. **执行摘要**：总体结论一句话 + 推荐路线一句话 +
   "最重要的发现"表（风险 × 结论 × 证据 × 建议，控制在一屏）
4. 主题章节（按审查对象组织：盘点/可行性/合规/平台/路线/风险）
5. **附录承载细节**：统计、明细、溯源、**复核命令**
   （让读报告的人能自己验证你的任何一条结论）
6. **未来两周 N 件事**：可执行、有顺序、能勾销——
   审查的终点不是"知道问题"，是"知道下一步"

## 复核命令（附录的灵魂）

每份审查报告附录里放一组**读报告的人可以直接复制运行的命令**
（哈希复核、构建命令、测试命令、检索命令）。
报告说"164 个文件一致"，就给出那 164 个文件怎么重新算。
**可复核，是审查报告和普通意见书的根本区别。**
