# 发布前自检（发布就绪核查清单）

进入发布议题时逐项核查。任何一项"没查"就标"没查"——
默认通过是发布事故的头号温床。每项给证据，不给感觉。

## 1. 权利链

- 所有商业资产（美术/音乐/字体/音效）的授权状态逐条登记：
  来源、授权类型、是否允许商用、是否需要署名。
- 玩法与表达的第三方渊源（致敬/换皮/改编）单独评估，
  需要时寻求正式法律意见——审查报告不代替法律意见。
- **待补证不上市**：权利链没闭环之前，其他全是白谈。

## 2. 构建链

- 正式构建逻辑全部纳入版本控制——构建入口指向临时目录/
  本地脚本 = 高风险（换台机器就构建不出来）。
- **干净检出验证**：全新 clone → 按 README 命令 → 构建成功。
  这是"别人能构建你的项目"的唯一证明。
- 版本号有唯一事实源，且与发布包一致。

## 3. CI 真实性

- CI 里每个步骤**真的在执行吗**？（命令存在、退出码正确传递、
  失败真的会让流水线变红）
- 断言**真的在断言吗**？（输出"PASS"字样 ≠ 校验了内容）
- "CI 是绿的"和"CI 在保护你"是两件事——后者要逐条验证。

## 4. 测试有效性

- 声称的验收条件，有没有测试真正覆盖？（"150 步教学全通"——
  脚本里有没有强断言，还是只打印了日志）
- 测试只存在命令或输出而没有有效覆盖的，按"未覆盖"登记。

## 5. 本地化

- 字典文件存在 ≠ 产品是完整多语言：逐界面核查正文、壳层、
  剧情、引导是否全覆盖。
- 关键语言需要母语者或实际布局验收（文字长度撑破 UI 是常态）。

## 6. 存档可靠性

- 写入有确认吗？失败会假成功吗？（玩家进度丢失是不可原谅事故）
- 版本迁移有 schema 和顺序吗？旧存档在新版本上会发生什么，
  测过吗？

## 7. 打包白名单

- 发布包用**白名单**打包（列出该进的），不用黑名单（列出不该进的）。
- 检查：源映射（.map 含 sourcesContent）、开发脚本、测试夹具、
  临时文件、密钥——有没有混进玩家包。
- 工程目录直接复制为发布包 = 高风险。

## 8. 平台适配

- 目标平台的硬要求逐项过： overlay/成就/云存档/离线行为/
  分辨率与输入/审核内容与分级。
- AI 生成内容的平台披露政策，按查询日期的最新版本核查。

## 收尾问题（写进裁决书）

1. 上述每项：已核实 / 待补证 / 未覆盖——各占几项？
2. 高风险项清零了吗？没清零凭什么发？
3. "未来两周 N 件事"是什么？
