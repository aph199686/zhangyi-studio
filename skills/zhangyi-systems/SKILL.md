# 张翼 · 机制与系统

机制阶段的核心纪律：**机制不是越多越好，是每一个都拔不出来才好。**
本 skill 的输出是《系统裁决书》。

前置：用户项目应已有 `zhangyi.config.md` 和病灶定义（立项裁决书）。
没有病灶定义的机制评审是无的放矢——先回 zhangyi-kickoff 立病灶，或当场
逼用户写出"这个机制要解决什么问题"。

## 工作流

### 1. 接过病灶与支柱

从项目的立项裁决书（`verdicts/`）读出病灶 P1/P2/P3 与设计支柱。
本阶段一切机制都必须挂在病灶上：先说治什么病，再说怎么治。

### 2. 机制细化：从把手到设计

新机制从哪来不重要（用户灵感 / 机制活检的可杂交把手 / 竞品借鉴），
落地前都要过细化四问：

1. **它放大内核，还是外挂系统？** 强化游戏内核发动机的机制优先；
   挂在内核外面的外围系统（养成、装饰性收集）默认可疑。
2. **它会诱发什么？** 推演三件事：玩家会因此做出什么行为、与已有机制
   会产生什么涌现反应、做这些行为时是什么情绪。推演得通的机制才进入细化。
3. **代价是什么？** 每个优势必须换一个明确的代价——没有代价的优势
   不是设计，是施舍，且一定会被玩家滥用到你后悔。
4. **玩家能预判吗？** 凡是系统施加的惩罚/淘汰/损失，玩家必须能提前
   计算和规避。算不出来的是天灾，不是机制；可预判的才叫博弈。

细则与判别示例见 [references/机制评审闸门.md](references/机制评审闸门.md)。

### 3. 数值纪律

机制里出现的每个数字按三分类标注：**已验证 / 占位 / 待验证**；
给机制显式标注**平衡旋钮**（"调这个参数就能救/杀这个机制的那几个数"）；
成本评估必须算隐性成本。细则见 [references/数值与平衡.md](references/数值与平衡.md)。

### 4. 环境约束检查

机制在哪个环境里跑？诚实检查，不护短：

- **单机对 AI**：AI 不理解"软信息"（暗示、传话、心理战）。依赖对手
  理解信息的机制，在单机下打对折甚至归零——要么给 AI 加理解模块
  （高成本，进待拍板），要么**降级为硬效果**（直接生效、不需要被理解）。
- **有争议的机制做成开关**：玩家群体可能分裂的机制，做成可选开关、
  默认关，让数据而不是争吵来决定。

### 5. 裁决与落档

落裁决按共享原语 [原语·落判](../zhangyi/references/原语·落判.md) 执行；
本阶段模板：`templates/系统裁决书.md`。

## 边界（与 zhangyi-probe 的分工）

本 skill 的推演全是纸面功夫。机制"有效"（规则上跑得通）可以被模拟验证，
机制"有趣"只能被真人验证——**在系统裁决书的诚实声明里，不许出现
"已验证好玩"**。需要模拟探针时，路由到 `zhangyi-probe`（结构化模拟验证），
并保留"探针能否决结构问题、不能证明好玩"的边界。

## 姿态

- 用户的直觉方案值得认真推演，但推演的结果可能是"这个方案在你自己的
  支柱下不成立"——如实说，引用支柱，不引用权威。
